# 전체 코드 점검 (2026-10-14)

저장소의 백엔드·프론트엔드·설정·테스트를 파일 하나씩 읽고 찾은 문제를 정리했다. **코드는 고치지 않았다.**

- 범위: `src/main`·`src/test`·`src/main/resources`·`frontend/src`·`frontend/e2e`·빌드/CI 설정 (`shared/ui/base` 의 shadcn 생성 파일 제외)

- 직접 다시 확인한 것: 아래 표에 **확인** 이라고 적은 항목은 코드를 열어 재현 경로를 따라가 봤다. **추정** 은 코드상 가능하지만 실행으로 재현하지는 않았다

① 정비·주유 폼이 화면에 보이는 것과 다른 주행거리를 저장하는 회귀, ② 공유 IP 에서 로그인이 잠기는 시도 제한 창,
③ 서버 500 이 로그 없이 사라지는 경로 셋이다.

## 2. 백엔드

### 2-1. 인증·사용자 (`user/`, `common/auth`, `common/web`, `common/config`)

**[중간] 시도 제한 창이 문서와 다르게 동작 — `LoginAttemptLimiter.java:92-96`**
- 카운터는 `Duration.between(attempt.lastAttempt, now) > WINDOW` 일 때만 0 이 된다. 즉 **마지막 시도로부터** 10분을 쉬어야 초기화되는 슬라이딩 방식이다.
- `LoginService.login` 은 `login-ip:` 키에 `acquireShared`(한도 50)만 부르고 성공해도 그 키를 비우지 않는다.
- 그래서 사무실·통신사 NAT 처럼 IP 하나를 여럿이 쓰면, 10분 미만 간격으로 이어진 **정상 로그인** 51번째에 그 IP 전체가 10분 잠긴다(9분 간격이면 약 7.6시간 뒤).
- `signup:`·`password-reset-ip:` 도 같은 성질(한도 10).
- README:319 "10분 안 10회 초과 시 10분 잠금" 과 다르다.
- 방향: 창 시작 시각을 두는 고정 창으로 바꾸거나, 성공한 로그인은 IP 키에서 빼거나, 최소한 문서를 실제 동작에 맞춘다.

**[낮음] 세션 id 교체보다 사용자 id 저장이 먼저 — `LoginService.java:42-44`**
- `setAttribute(LOGIN_USER_ID)` → `changeSessionId()` 순서이고 `flush-mode: immediate` 라, 아주 짧은 순간 **옛 세션 id** 가 로그인된 상태로 DB 에 저장된다.
- 세션 고정 공격 창이 매우 짧아 실제로 노리기는 어렵다. 순서만 바꾸면 된다.
- `UserControllerTest.loginSuccessStoresSessionAndRotatesId` 는 이름과 달리 id 교체를 확인하지 않는다(요청 전에 세션이 없음).

**[낮음~중간, 영향은 추정] BCrypt 가 트랜잭션 안에서 돈다 — `UserService` login·verifyPassword·changePassword·signUp**
- JPA 트랜잭션은 시작할 때 커넥션을 잡는다. 틀린 비밀번호 요청 10개가 동시에 오면 Hikari 기본 풀 10개가 BCrypt 시간 동안 바닥난다.
- `changePassword` 는 사용자 행 잠금까지 쥔 채 BCrypt 를 세 번(현재 확인·같은지 확인·새 해시) 돈다.
- 방향: 조회만 트랜잭션 안에서, `matches`·`encode` 는 밖에서.

**[참고] `PasswordResetService.request()` 도 클래스의 readOnly 트랜잭션을 탄다 — `:37`, `:104`**
- "요청 스레드는 횟수만 센다"는 문서와 달리 매번 커넥션을 빌린다. DB 장애 때는 "언제나 204" 대신 500.
- 방향: `confirm` 처럼 `Propagation.NOT_SUPPORTED`.

**[낮음] 커밋 뒤 세션 끊기가 실패하면 이미 성공한 변경에 500 — `PasswordResetService:209-214`, `UserController:89`**
- `afterCommit` 안의 예외는 호출자에게 전파된다. 비밀번호는 바뀌고 토큰은 사용 처리됐는데 응답은 500, 다시 시도하면 "만료된 링크", 다른 기기 세션은 살아 있다.

**[낮음, 추정] 만료 토큰 정리 DELETE 가 인덱스 없이 표를 훑음 — `PasswordResetTokenRepository:34`**
- `expires_at` 인덱스가 없어 REPEATABLE READ 에서 next-key 잠금이 넓게 걸린다. 다른 주소의 발급과 데드락 가능성. 재시도·catch 로 흡수되지만 두 번 지면 메일이 조용히 안 간다.

**[참고] 기존 백로그 "이메일 단위 표적 잠금" 범위 확대**
- 남의 주소로 재설정을 10번 요청하면 그 사람도 10분 동안 재설정 메일을 못 받는다. 백로그에는 로그인만 적혀 있다.

**[낮음, 잠재] `LoginUserArgumentResolver.java:16-19` 가 `Long` 타입일 때만 동작**
- 누군가 `@LoginUser long`·`String` 으로 쓰면 이 리졸버가 빠지고 스프링 기본 리졸버가 `?userId=` 쿼리로 채운다(규칙 10 우회). 지금 24곳은 모두 `Long` 이라 피해는 없다.
- 방향: 애노테이션만으로 지원 여부를 정하고, 타입이 다르면 예외.

**[참고] 배포 시점에 볼 것**
- prod 에 `server.forward-headers-strategy` 가 없어 TLS 를 끝내는 프록시 뒤에서는 HSTS(`request.isSecure()`)가 나가지 않는다.
- `SecurityHeadersFilter` 에 `@Order` 가 없어 413(`RequestSizeLimitFilter`)·CSRF 403 응답에는 보안 헤더가 빠질 수 있다.
- CSRF double submit 은 화면과 API 가 같은 호스트일 때만 동작한다(`client.ts:40` 이 `document.cookie` 로 읽음). API 를 다른 호스트로 나누면 모든 쓰기가 `CSRF_REJECTED`. 같은 출처 배포를 전제로 문서화할 것.

**[참고] 주석·문서 불일치**
- `SecurityHeadersFilter` 의 Referrer-Policy 주석 "재설정 토큰 주소 보호" — 이 헤더는 API 응답에만 붙고, 실제 보호는 `frontend/index.html:8` 의 meta 태그가 한다.
- `PasswordResetMailer.java:67` "from 이 비면 spring.mail.username 사용" — `from` 자체가 `${spring.mail.username:}` 이다.
- `PasswordResetMailer.java:74` `switch` 문에 default 가 없어, 언어가 늘면 제목·본문이 빈 메일이 조용히 나간다(switch 식이면 컴파일러가 잡음).
- `User` 에 `@Version` 이 없고, 프로필 저장이 동시에 바뀐 비밀번호를 되돌리지 않는 것은 MariaDB `innodb_snapshot_isolation=1` 덕분이다(`UserConcurrentUpdateTest:19`). 이 의존이 CLAUDE.md 에 없다.

### 2-2. 차량·차고·정비 (`vehicle/`, `garage/`, `maintenance/`)

소유권 검사, 모든 쓰기 경로의 `findOwnedVehicleForUpdate`, 삭제 순서·FK, 정렬 화이트리스트, LAZY, `InputText`, null/0 구분은 규칙대로였다.

**[설계 판단] 계기판 교체 뒤 다음 정비 km 판정 — `Vehicle.java:97-103`, `NextService.java:112-118`**
- `correctOdometer` 주석은 "계기판 교체·자리수 오타용"이다. 그런데 `NextService` 는 `record.getServiceOdometer() + intervalKm` 를 새 계기판 값과 그대로 비교한다.
- 예: 150,000km 에 타이밍벨트(10만km 주기) 교체 → 계기판 교체로 0 으로 정정 → 다음 교체가 250,000 이라 새 계기판으로 25만km 를 타야 "지남".
- 방향: 주석에서 "계기판 교체"를 빼고 오타 전용으로 좁히거나, 정정 시점을 기준점으로 남겨 그 이전 기록의 km 판정을 끈다. 주유 연비 구간도 같은 전제(단조 증가)다.

**[낮음] 등록·수정 검증이 줄바꿈에서 갈림 — `VehicleUpdateRequest.java:16,20,24`**
- 등록은 `@NotBlank` 라 `"A\nB"` 가 201, 수정은 `@Pattern(".*\\S.*")` 의 `.` 이 줄바꿈과 안 맞아 400 "공백만으로는 설정할 수 없습니다".
- 방향: `(?s).*\S.*` 로 바꾸거나 양쪽 모두 제어 문자를 막는다.

**[낮음] 차량 등록이 사용자 행을 잠그지 않음 — `VehicleService.java:31-48`**
- 같은 사용자의 탈퇴와 겹치면 FK 위반 → 500(추정, 자기 두 탭에서만). 규칙 13 의 잠금 목록에 등록이 없다는 점만 기록.

**[참고] 잠금이 소유권 확인보다 먼저 — `VehicleService.java:119-131`**
- `findLockedByPublicId` 가 남의 차 행도 잠근 뒤 404. 공개 id 가 무작위라 실질 위험은 낮다.

**[참고] 기록이 많을수록 느려지는 목록 — `VehicleListService.java:55-57`**
- 차량 목록 한 쪽을 볼 때마다 소유자의 정비 이력 전체를 엔티티로 읽는다(홈 요약도 같음). 쿼리 수는 고정이지만 응답 시간·메모리가 이력 수(최대 2만)에 비례.

**[참고] 주기 상한 `500_000`·`120` 이 상수 없이 세 곳에** — `ServiceIntervalRequest.java:14,19`, `AccountRestoreRequest.java:56-57`, 프론트 `NextServiceCard.tsx:210,227`. `InputLimits`·`limits.ts` 로 옮길 후보.

**[낮음] 낡거나 틀린 주석**
- `VehicleRepository.java:17` "탈퇴 전용 전체 조회" — 실제로는 내보내기·홈 요약이 쓰고, 탈퇴는 `findLockedByOwnerId`.

### 2-3. 주유·요약·계정 (`fuel/`, `summary/`, `account/`)

연비 계산(기준점, 첫 주유량 제외, 불가능 연비 제외), 잠금 순서, 통화 기록별 처리, 계산값 비저장은 규칙대로였다.
가져오기와 등록의 규칙(InputText·미래 날짜·`liftOdometerTo`·숫자 제약·빈 주기)도 연식 하나를 빼고 일치했다.

**[낮음~중간, 잠재] 연식 없는 차가 있으면 내보내기 → 가져오기가 통째로 400 — `AccountRestoreRequest.java:37`**
- 가져오기는 `@NotNull @Min(1900) @Max(2100) Integer modelYear`. DB(V1)는 `DEFAULT NULL`, 내보내기와 프론트 타입은 null 을 그대로 싣는다.
- 한 대라도 걸리면 전체 롤백이라 다른 차량 기록도 못 들어간다. 같은 번호판으로 합치는 경로(연식을 쓰지 않음)도 막힌다.
- **지금 운영 DB 에서 `model_year IS NULL` 은 0대**(2026-10-14 조회). 그래서 지금 당장 터지지는 않는다.
- 방향: 가져오기에서는 null 허용(범위 검사만 유지), 내보내기 → 가져오기 왕복 테스트로 막는다.

**[낮음] 새 차량에 기준점을 개수 검사 없이 복원 — `AccountRestoreService.java:156-159`**
- 2026-10-04 이전 백업에는 한 차량에 기준점이 여럿 있을 수 있고 그대로 되살아난다. 계산은 최신 하나만 써서 숫자는 맞지만 "차량당 하나" 불변식이 깨진다.

**[참고, 추정] 가져오기 중복 판정이 트랜잭션 첫 스냅숏을 봄 — `AccountRestoreService.java:113-119,143-146`**
- 그 사이 같은 차량에 커밋된 일반 주유가 `existing` 에 안 보여, 내용이 완전히 같을 때만 중복 1건이 생길 수 있다.

**[참고] 0으로 나누기 방어 비대칭 — `FuelRecordResponse.java:50-53`**
- `liters != null` 만 보고 나눈다. `FuelSegment` 는 `<= 0` 까지 막는다. API 로는 못 들어오지만, 손으로 0L 을 넣으면 그 차량 주유 목록 한 쪽 전체가 500.

**[참고] 정렬 없는 차량 목록 — `AccountExportService.java:55`**
